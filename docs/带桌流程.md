# 带桌流程（店长 / 常驻 KP）

## 先划边界：这套东西能替代什么、不能替代什么

| 店里的活 | 这套框架 | 说明 |
| --- | --- | --- |
| 备团、写剧情 | **替代不了** | 剧本还是要人写；框架只管剧本怎么装进来 |
| 记数值、记主线、记承诺 | 能替 | 单一来源 + L0/L1/L2，比人脑稳 |
| 查判定、查判例、算成功率 | 能替 | 日志 + `export_stats.py` |
| 现场读空气、救场、把烂梗变成好戏 | **替不了** | 这是带团的核心，也是 AI 现在最差的部分 |
| 4–6 人同桌、实时插话、分屏私聊 | **替不了** | P1 只验证了单人；`05-玩家私有/` 是文件分流，不是通信通道 |
| 内容分级、版权合规 | 只能提醒 | 政策写进文档不等于护栏，店里要自己审 |

结论：**它省的是记录与一致性成本，不是讲课与救场的成本。** 想靠它少雇一个 KP，目前做不到；想靠它让一个 KP 同时开三桌且不记错，可以。

## 开一场的最短路径（15 分钟）

1. 选剧本：`scenarios/` 里挑一个已接入的，确认 `剧本形态` 与 `规则系统`。
2. 车卡：用 `keeper/roles/车卡向导.md` 带新人一格格填，派生值当场算完。
3. 审核：按 `systems/<系统>/车卡规格.md` 逐条过，数值 + 叙事两关。
4. 建会话：`python tools/new_session.py --scenario <剧本id> --system coc7 --persona 温柔引导者`
5. 预检：`python tools/check_session.py sessions/<session_id>`，红色项不给开局。
6. 打包与开局：`python tools/pack_session.py sessions/<session_id> --with-docs` → 打开 `dist/<session_id>/` 从 `START.md` 起 KP。
7. 单人在场时，先过 `docs/单人玩法.md` 的五条，别拿多人本硬塞一个人。

## 卡池

- `characters/` 是母本，存**审核通过**的卡，卡头写明 `规则系统` 与强度等级。
- 一桌开团从卡池复制到 `01-车卡/`，本团的伤害、成长只改副本。
- **跨系统不可复用**：COC 的卡不能直接进 D&D 团，要按目标系统重车。
- 同一张卡可以带多个团，但各团的经历互不可见——这是隔离的一部分。

## 缺席与人员流动

处理表写在每次团的 `00-本次设定.md` 里，默认：

| 情况 | 处理 |
| --- | --- |
| 单场缺席 | 角色暂离，给一句合理去处，回来时归队 |
| 连缺两场 | 降为 NPC，KP 代管，不判定、不受伤害 |
| 中途加入 | 现场车卡 + 审核，以本地人或接到委托入场 |
| 角色死亡 | 新角色同强度入场，或转旁观 |
| 玩家代打 | 代打者只声明行动，判定仍归 KP |

## 多桌并行

- 一桌一个会话文件夹，`sessions/YYYY-MM-DD-<剧本id>-NN`，NN 递增。
- 桌与桌之间**不共享** `04-KP私有.md`、`05-玩家私有/`、状态跟踪。
- 同一剧本开多桌时，剧情后果不互通：A 桌死了的 NPC，在 B 桌仍然活着；A 桌揭开的真相不进入 B 桌。
- 想跨桌延续（同一世界观连续团），就把它做成**同一个会话的连续场次**，而不是两个会话。

## 数据

`python tools/export_stats.py sessions/ --out stats.csv`，导出字段：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| session_id / 场次 | 日志 frontmatter | 排期与复盘 |
| 时长分钟 | 日志 frontmatter | 哪一幕拖时间 |
| 检定数 / 暗投数 | 日志检定表 | 判定密度是否失衡 |
| 失败数 / 失败率 | 日志检定表 | 难度是否过严 |
| 主线节点 | 日志 frontmatter | 每场推进了多少 |
| 审核退回数 | 角色卡审核记录 | 车卡规格是否过严或过松 |

日志是事后录入的，统计反映的是记录质量，不是精确采集。

## 长团维护（每 3 场 5 分钟）

1. `python tools/archive_logs.py sessions/<会话>`：旧日志移入 `03-日志/归档/`，不删除。
2. `python tools/check_drift.py sessions/<会话>`：连续两场无主线推进、承诺超期、观察区到期、指针失效、L0 超预算。
3. 看 `前情提要.md` 的压缩记录：上一次压缩是哪一场，到点就补一块 L2。
4. 丢弃清单扫一遍：本场剧本会用到的，复活。

## 纠纷兜底（谁来裁定）

- 场内：判例表，同一场不重复讨论。
- 场后：KP 或店长复核，误判按 `keeper/_framework.md` 第 7 节三档补偿（回补 / 补给 / 重开）。
- 店里：需要第三方时由店长出面，但**这套框架不提供第三方机制**，只有文件和流程，靠人执行。


## 结团复盘（30 分钟）

1. 主线节点是否全部推进，哪一条靠保底路径过的。
2. 哪条线索全场没人查，是设计问题还是表述问题。
3. 判例里有几条被复核修订，修订原因归到 `keeper/_framework.md` 还是规则包。
4. 值得回流的 NPC、桥段合并回 `scenarios/` 母本并升版本。

## 内容与版权

带店内顾客（尤其有未成年）时，先定 `内容分级` 并写进 manifest；喊停机制见 `keeper/_framework.md` 第 9 节。外部下载的模组不进仓库，见 `docs/内容与版权.md`。
