# 项目路线

## P1 · 单机版（当前目标）

**形态**：单人。把整个文件夹放到本地、用豆包打开，选一个本就能自己玩。一个文件夹就是一份完整的团，1 名玩家 + AI 当 KP，单屏纯文本。

**范围**：剧本接入、车卡审核、KP 纪律（信息 / 判定 / 明暗投 / 抗嘴炮 / 注意力分层）、逐场记录、断点续跑。

**不做**：多人同桌、分屏私聊、实时语音、多桌并行、缺席管理。相关文件保留在模板里，但不进 P1 验收。

**验收标准**：

1. 冷启动：`tools/pack_session.py` 打出最小包 → 豆包打开 `dist/<session_id>/` → 按 `START.md` 走，全程不需要额外工具（掷骰可让 KP 自掷，日志标「未审计」）。
2. 一个本能连续跑 3 场以上不跑偏：主线按节点推进，即兴事件不升级、不反复给戏；`tools/check_drift.py` 连续两场无主线推进即报漂移。
3. 数值不越界：不合规的卡在开局前被审核拦住（`check_session.py` 卡住未过审 + 人数与卡数不符）。
4. 断点续跑：新开一个会话，只装载 `前情提要.md` + `状态跟踪.md` + 最新一份日志，能接上上一场。
5. 结团后能导出一次统计（场次、时长、检定数、明暗投、失败率）。

**P1 的七条硬约束**（不满足就不算合格的单人团）：

| 约束 | 落点 |
| --- | --- |
| 单人不能卡在按 3–4 人写的节点 | 概览写 `单人可跑` 字段；`docs/单人玩法.md` 五条适配与三回合战斗预算 |
| 模型不能看见整个仓库 | `pack_session.py` 物理打包成最小包 |
| 骰值必须可审计 | 三档骰源 + `roll.py`（时间戳 + 种子），不设半明投 |
| 数值不能双写 | 单一来源：数值只存卡，状态跟踪只存非卡面 |
| L0 预算要撑得住长团 | 单人 90 行 / 六人 150 行两档预算 + 降级顺序 |
| 日志归档不能靠人工 | `archive_logs.py` 机械归档，只移动不删除 |
| 三问误判必须可逆 | 丢弃留痕 + 观察区 + 复活 |

## P2 · QQ 群版（P1 验收通过后）

**形态**：把 KP 设成一个人设，接入 QQ；一个群 = 一次跑团。依托已有的 DSH / QQ 接入方式改造。

**复用**：剧本、规则包、KP 纪律、审核与判例、日志格式。**改造**：会话隔离从文件夹迁到群维度、多人私有通道、多群并发、消息粒度与节奏。

**前置**：P1 五条验收全过，才动 P2。

## P3 · 独立界面版（思路，不排期）

自带界面，不依托豆包：买一份 API key 写进项目配置，界面读同一个文件夹（剧本 / 规则 / 会话），自己发请求、自己渲染。框架层文件不改，只换运行时与交互壳。

## P4 · APP 版（思路，不排期）

把 P3 的界面打包成手机 APP。前置：P3 的请求层与存储路径跑通；P1 的记忆与隔离规则不变。
